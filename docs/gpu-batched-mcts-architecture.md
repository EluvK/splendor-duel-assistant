# 《璀璨宝石：对决》GPU 批处理 MCTS 推演架构设计规范

> **文档定位**：本项目（Splendor Duel AI）基于 Rust 向量化状态机与 PyTorch CUDA 批前向加速的高性能大规模自博弈推演架构技术规范。  
> **核心参考**：KataGo、Leela Chess Zero (LCZero)、AlphaGo Zero 的跨局批处理推演范式（Inter-Game Batched MCTS）。

---

## 1. 架构目标与核心理念

在棋盘博弈强化学习自博弈中，若每局游戏使用独立线程同步调用神经网络，GPU 每次前向前仅有极少待评估盘面（Batch=1~2），会遭遇严重的核函数启动与调度通信开销。

为了彻底释放现代 GPU Tensor Core 的高并行计算吞吐，本项目采用 **跨局向量化事件循环（Vectorized Event-Driven Step Loop）**：
- **CPU 原生轻量逻辑**：单调度线程集中轮询驱动 64~128 局活跃游戏的状态机转移、规则判定、PUCT 选择与树更新；
- **批评估汇聚（Batched Forward）**：在每个推演波次统一收集处于叶子节点或根节点等待评估的盘面，拼装为连续扁平切片 `[B, 1005]`（$B \in [32, 128]$）；
- **GPU 高效密集推理**：一次性推入 PyTorch CUDA 执行 AMP FP16 半精度批量前向，单次批推理耗时仅 1~2 ms；
- **批量回填与推进**：将预测结果按索引精确切片并广播回流至各局 MCTS 节点，批量完成展开（Expansion）与价值回溯（Backup）。

## 2. 批推演总体架构

整体系统解耦为 **“Rust CPU 向量化逻辑调度池”** 与 **“PyTorch GPU 批前向引擎”**，两者通过 PyO3 连续内存切片交互：

```
┌────────────────────────────────────────────────────────────────────────┐
│               CPU 侧：64~128 局并发向量化状态机池 (Rust Native)         │
│                                                                        │
│   [Worker 01]  [Worker 02]  ...  [Worker 64]  ...  [Worker 128]        │
│        │            │                   │                │             │
│        ├─ 规则生成 (legal_actions, ~2μs)│                │             │
│        ├─ 单动作快速推进 (step, ~0.3μs) │                │             │
│        └─ PUCT 选支 (select, ~10μs)     │                │             │
│                   │                                      │             │
│                   ▼ 待评估盘面 (Root/Leaf obs, 1005维 f32)▼             │
└───────────────────┬──────────────────────────────────────┬─────────────┘
                    │                                      │
                    ▼                                      ▼
┌────────────────────────────────────────────────────────────────────────┐
│               Batch Aggregator (平坦内存批收集器)                       │
│                                                                        │
│   • 统一轮询活跃 Worker，捕获所有 WaitingRootEval / WaitingLeafEval     │
│   • 扁平切片预分配组装：batch_obs [B, 969] 与 batch_indices [B]         │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
                                    ▼ PyO3 零拷贝视图传递 (PyArray1)
┌────────────────────────────────────────────────────────────────────────┐
│               GPU 侧：PyTorch CUDA 批前向引擎 (GpuBatchedEvaluator)     │
│                                                                        │
│   • 模型驻留 GPU 显存 (SplendorNet, AMP FP16 自动半精度)               │
│   • 批量输出：Logits [B, 1856], Win [B, 1], Turns [B, 1], Reason [B, 3]│
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
                                    ▼ 结果广播与状态推进
┌────────────────────────────────────────────────────────────────────────┐
│  按 batch_indices 分发 ➔ 批量执行 Node Expansion & Backup ➔ 下一模拟波次 │
└────────────────────────────────────────────────────────────────────────┘
```

## 3. 核心机制与关键技术

### 3.1 向量化单线程状态机设计
- **无 OS 线程锁争用**：
  传统 Thread-per-game 架构需要使用互斥锁、通道或线程池同步等待，上下文切换开销巨大。本项目使用单调度线程驱动 `Vec<GameWorker>`，每个 Worker 维护明确的状态机枚举：
  - `Idle`：当前局结束，等待派发新对局；
  - `AtDecision`：当前轮次决策起点，处理终局检测、微步折叠或初始化 MCTS；
  - `WaitingRootEval`：根节点就绪，等待批量送入 GPU 获取策略先验与初评价值；
  - `Simulating`：MCTS 模拟推进中（执行 PUCT Selection 与无损早停判断）；
  - `WaitingLeafEval`：叶子节点就绪，等待批量送入 GPU 评估。
- **调度时间分布**：
  单步决策中，CPU 端仅执行纳秒/微秒级的规则检查与数组索引更新，大部分实际耗时由 GPU 密集矩阵乘法主导，单核即可轻松打满 128 局并发推进。

### 3.2 内存与显存设计规格

| 资源项 | 128 局并发占用 | 说明 |
| :--- | :--- | :--- |
| **Rust 游戏状态池** | **< 1 MB** | 单个 `GameState` 仅约数百字节，128 局常驻开销极小 |
| **MCTS 树结构内存** | **150 ~ 300 MB** | 128 个 Worker 各自维护私有浅树（每步访问节点数十至数百个），完成一步后即时释放重置 |
| **转置表缓存 (EvalCache)** | **~ 32 MB** | 每个 Worker 独立维护容量为 2048 的 LRU 转置表缓存，大幅削减同局内重复盘面评估 |
| **GPU 显存 (VRAM)** | **~ 1.8 GB** | 模型参数（5MB） + Batch=128 激活值与中间张量（数百MB） + CUDA 运行上下文 |

### 3.3 跨语言接口与内存契约
1. **输入契约**：Rust 将 `batch_obs` 组装为连续一维切片 `&[f32]`，长度为 `B * 1005`，通过 PyO3 `PyArray1::from_slice` 构建只读视图，传入 Python 评估器；
2. **GPU 批推理**：Python 侧将平坦数组变形为 `[B, 1005]` 推入 GPU，在 `torch.no_grad()` 与 `torch.amp.autocast('cuda')` 环境下完成前向传播；
3. **输出契约**：Python 侧将 `logits`、`win`、`turns`、`reason` 展平为连续内存 NumPy 数组返回给 Rust，Rust 侧通过严格维度断言校验后按 `batch_indices` 分发回各 Worker。

## 4. 预期性能指标规范

| 关键指标 | CPU 基准 (AVX2 单核) | GPU 批处理 (128 并发) |
| :--- | :--- | :--- |
| **MCTS 决策吞吐** | ~ 150 步/秒 | **3,000 ~ 6,000 步/秒** |
| **单局对弈生成耗时** | ~ 2.2 秒 | **< 0.15 秒 (等效并发耗时)** |
| **单轮自博弈迭代 (50 局 MCTS-30)** | ~ 60 秒 | **5 ~ 8 秒 ⚡** |
| **GPU Tensor Core 利用率** | 0% | **80% ~ 95%** |
